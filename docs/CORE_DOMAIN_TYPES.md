# Flight Safety Monitor & Verification Platform

## Phase 2B-1A — Core Domain and Value Type Design

**Status:** Reviewed and accepted for Phase 2B-1B
**Lifecycle phase:** Phase 2 — Architecture and interface design
**Implementation status:** No monitor implementation authorized by this document
**Baseline dependency:** Phase 2B-0 / Phase 2B-0A interface representation decisions
**Scope:** Synthetic, non-operational verification platform only

---

# 1. Purpose

This document defines the concrete C++20 domain/value types that form the
lowest-level deterministic-core interface vocabulary.

It converts the reviewed Phase 2B representation decisions into inspectable
type contracts before runtime-event, decision-record, rejection-evidence,
initialization, reset, or coordinator APIs are finalized.

This increment is intentionally limited to:

- modeled time and duration;
- navigation ordering and event-reference identities;
- navigation-observation schema-version metadata;
- configuration identity;
- Cartesian position and velocity;
- navigation validity and source health;
- navigation observation;
- synthetic axis-aligned envelope;
- immutable monitor configuration;
- optional-value semantics;
- checked modeled-time arithmetic;
- projection-duration conversion semantics;
- domain-level validation boundaries.

No monitoring algorithm or state-owning monitor component is implemented here.

---

# 2. Governing Constraints

The type design shall preserve the existing baselines:

1. modeled time is explicit and synthetic;
2. host wall-clock time has no decision authority;
3. exact modeled-time equality and ordering are required;
4. same-time runtime events remain representable;
5. modeled-time storage uses nanoseconds;
6. `ScenarioTime` uses signed 64-bit storage;
7. `ScenarioDuration` uses unsigned 64-bit storage;
8. logical navigation sequence uses unsigned 64-bit storage;
9. sequence rollover is unsupported in the initial core;
10. physical position, velocity, projection, and envelope bounds use C++
    `double`;
11. physical values used as navigation input or envelope bounds must be finite;
12. position and velocity remain distinct domain values;
13. optional absence shall not use sentinel values;
14. navigation-observation schema version is metadata only in the current
    baseline;
15. configuration identity is caller supplied and shall not be generated by the
    deterministic core;
16. configuration thresholds have no silent defaults;
17. configured duration zero is structurally valid;
18. envelope bounds require strict per-axis minimum less than maximum;
19. no arbitrary operational or defensive configuration maxima are introduced;
20. non-finite projection output is not classified as `INSIDE` or `OUTSIDE`;
21. the core remains synthetic and non-operational.

# 3. Design Principles

## 3.1 Strong types for semantically different integral domains

Integers with different meanings shall not be represented as interchangeable
raw integer parameters at public deterministic-core boundaries.

The initial design therefore uses distinct strong values for:

- `ScenarioTime`;
- `ScenarioDuration`;
- `NavigationSequence`;
- `RuntimeEventReference`;
- `NavigationObservationVersion`.

Equal underlying storage does not imply semantic interchangeability.

## 3.2 Domain distinction without a generic units framework

The project needs explicit meter and meter-per-second semantics, but it does not
currently need a generic dimensional-analysis library.

The initial design therefore distinguishes:

- `Position3`;
- `Velocity3`;

and uses unit-bearing member names.

It does not introduce:

- generic vectors;
- matrices;
- unit-template frameworks;
- dimension libraries;
- operator-heavy vector algebra.

## 3.3 Explicit ownership

Values crossing deterministic-core boundaries should own their data where
practical.

A public domain value shall not depend on caller-managed transient storage
unless a later measured need justifies a view type.

## 3.4 Validation is semantic, not policy inflation

Domain validation shall enforce only constraints required by the current
semantics.

It shall not invent:

- operational aerospace thresholds;
- arbitrary positive minima;
- arbitrary maximum durations;
- arbitrary maximum coordinate magnitudes;
- unbaselined cross-field threshold relationships.

## 3.5 Construction and access surface

The public domain vocabulary shall require intentional initialization.

For the integral strong values:

- default construction is not part of the public domain contract;
- construction from the exact underlying integer type is explicit;
- implicit conversion from a raw integer is prohibited;
- implicit conversion back to a raw integer is prohibited;
- a read-only accessor exposes the underlying value when an adapter, test, or
  arithmetic helper genuinely requires it;
- zero remains a valid value where the domain permits zero, but zero shall be
  supplied intentionally rather than appearing through a default constructor;
- equality and ordering operators are provided only where Section 18 assigns
  those semantics.

The integral wrappers are pure value types. Their construction, accessors,
equality, and authorized ordering operations should be `constexpr` and
`noexcept`.

`ConfigurationIdentity` likewise requires explicit owned-string construction
and read-only access. It is not implicitly constructed from, or converted to,
`std::string` or `std::string_view`.

An empty `ConfigurationIdentity` remains intentionally representable so the
configuration validator can reject it deterministically. The type constructor
does not silently normalize or repair it.

Composite domain values whose fields are all required, including:

- `Position3`;
- `Velocity3`;
- `NavigationObservation`;
- `AxisAlignedEnvelope`;
- `MonitorConfiguration`;

shall require callers to provide every required field intentionally. Public
default construction shall not silently manufacture a semantically meaningful
all-zero object or configuration.

The larger composite field-layout code blocks in this document describe
required stored values. They do not authorize public mutable fields,
omitted-field defaults, or aggregate default construction.

For the strong scalar/string wrappers and Cartesian physical values, the
conceptual public-surface blocks explicitly show the intended constructor and
read-only-accessor shape. Concrete implementation may define those members
inline or out of line without changing their domain semantics.

# 5. Modeled Time

## 5.1 `ScenarioTime`

Conceptual public surface:

```cpp
class ScenarioTime final {
 public:
  explicit constexpr ScenarioTime(std::int64_t nanoseconds) noexcept;

  [[nodiscard]]
  constexpr std::int64_t nanoseconds() const noexcept;

 private:
  std::int64_t nanoseconds_;
};
```

Semantic contract:

- represents one absolute instant in the synthetic scenario-time domain;
- does not represent UTC, Unix time, host monotonic time, or wall-clock time;
- all `std::int64_t` values are representable domain values;
- no sentinel time value is reserved;
- comparison is exact integer comparison;
- same-time values are valid;
- negative values are representable and do not imply an error;
- construction does not read any clock.

Required public operations are limited initially to same-domain equality and
ordering plus checked elapsed-duration calculation.

The design shall not implicitly convert `ScenarioTime` to:

- `std::int64_t`;
- `ScenarioDuration`;
- floating-point seconds;
- host clock types.

The read-only `nanoseconds()` accessor exposes the stored nanosecond value when
required by tests, adapters, or serialization.

## 5.2 `ScenarioDuration`

Conceptual public surface:

```cpp
class ScenarioDuration final {
 public:
  explicit constexpr ScenarioDuration(std::uint64_t nanoseconds) noexcept;

  [[nodiscard]]
  constexpr std::uint64_t nanoseconds() const noexcept;

 private:
  std::uint64_t nanoseconds_;
};
```

Semantic contract:

- represents a non-negative modeled duration;
- all `std::uint64_t` values are representable;
- zero is valid;
- no sentinel value is reserved;
- it is not interchangeable with `ScenarioTime`;
- it does not imply host execution duration.

Configured freshness, timeout, persistence, and projection-horizon values use
this same duration domain because their current semantics are all non-negative.

## 5.3 Full-domain elapsed-time representability

For ordered signed 64-bit scenario times, the greatest possible difference is:

```text
INT64_MAX - INT64_MIN = UINT64_MAX
```

Therefore `ScenarioDuration` can represent the exact elapsed nanosecond
difference between any two ordered representable `ScenarioTime` values.

The implementation shall not obtain that value by first performing potentially
overflowing signed subtraction.

# 6. Checked Modeled-Time Arithmetic

The initial domain arithmetic surface should be deliberately narrow.

## 6.1 Ordered elapsed duration

Conceptual signature:

```cpp
[[nodiscard]]
constexpr std::optional<ScenarioDuration> checked_elapsed_between(
    ScenarioTime later,
    ScenarioTime earlier) noexcept;
```

Contract:

- if `later < earlier`, returns `std::nullopt`;
- otherwise returns the exact non-negative nanosecond difference;
- `std::nullopt` represents only the unordered/regressive argument relation;
- arithmetic overflow is not a second failure mode because every ordered pair
  of representable `ScenarioTime` values has a representable
  `ScenarioDuration`;
- the calculation shall be implemented without signed-overflow undefined
  behavior;
- equality returns a zero duration.

`std::optional` is sufficient because this operation has exactly one
no-result condition and no error payload is needed. A custom result hierarchy,
exception, or C++23-style `expected` abstraction would add machinery without
adding information to the C++20 domain contract.

A precondition-only subtraction API is not selected because the deterministic
core benefits from making a regressive argument pair explicit rather than
turning it into undefined, asserted, or silently saturated arithmetic.

This function is domain arithmetic only.

It does not decide whether a regressive runtime event is accepted or rejected.
The owning runtime-event path may map the `std::nullopt` result to the
appropriate existing rejection semantics and evidence.

## 6.2 No unchecked time-plus-duration operator

Phase 2B-1A does not introduce a general unchecked:

```text
ScenarioTime + ScenarioDuration
```

operator.

Current freshness, silence, and persistence comparisons can be expressed using
checked elapsed durations without requiring potentially overflowing absolute
time addition.

If later interface work demonstrates a real need for absolute time plus
duration, that operation shall be introduced as an explicitly checked domain
operation rather than an unchecked arithmetic operator.

# 7. Ordering and Evidence Identity Values

## 7.1 `NavigationSequence`

Conceptual public surface:

```cpp
class NavigationSequence final {
 public:
  explicit constexpr NavigationSequence(std::uint64_t value) noexcept;

  [[nodiscard]]
  constexpr std::uint64_t value() const noexcept;

 private:
  std::uint64_t value_;
};
```

Contract:

- equal value means duplicate relative to the compared accepted observation;
- lower value means regression/reordering;
- higher value means forward progress;
- gaps are observable;
- all `std::uint64_t` values are representable;
- no sentinel is reserved;
- maximum value does not authorize wrap to zero;
- rollover arithmetic is not part of the initial type.

The type itself does not decide navigation-state replacement.

## 7.2 `RuntimeEventReference`

Conceptual public surface:

```cpp
class RuntimeEventReference final {
 public:
  explicit constexpr RuntimeEventReference(std::uint64_t value) noexcept;

  [[nodiscard]]
  constexpr std::uint64_t value() const noexcept;

 private:
  std::uint64_t value_;
};
```

Contract:

- caller supplied for every submitted normal runtime event;
- all `std::uint64_t` values are representable;
- no sentinel is reserved;
- preserved verbatim in normal or rejected-event evidence;
- uniqueness within one initialized execution is a caller/event-source contract;
- the deterministic core does not maintain a historical set solely to enforce
  uniqueness;
- the value does not determine runtime-event ordering, navigation acceptance,
  persistence, or action behavior.

The core shall not increment or derive it.

Contract:

- represents navigation-observation schema version metadata only;
- all `std::uint16_t` values are representable;

- it is not a deterministic-core software revision.

# 8. Configuration Identity

## 8.1 Resolved representation

The Phase 2B-1A concrete representation is an owned strong string value.

Conceptual public surface:

```cpp
class ConfigurationIdentity final {
 public:
  explicit ConfigurationIdentity(std::string value);

  [[nodiscard]]
  const std::string& value() const noexcept;

 private:
  std::string value_;
};
```

This resolves the remaining Phase 2B-0 storage decision.

## 8.2 Why owned `std::string`

The selected representation preserves the earlier preferred opaque stable-string
identity while giving the deterministic core clear ownership.

Compared with alternatives:

### Numeric counter

Rejected for the initial interface because it makes identity meaning depend on
external lifecycle/counter state and is less inspectable in verification
evidence.

### Fixed-capacity character array

Rejected because no justified maximum configuration-identity length currently
exists. Selecting one solely for implementation convenience would create an
arbitrary policy limit.

### `std::string_view`

Rejected for the owned core domain value because it does not own storage and
would introduce caller-lifetime coupling into immutable execution
configuration.

### Content hash

Rejected because canonical configuration encoding and serialization remain
deferred and hashing is not required merely to produce traceability identity.

## 8.3 Identity validity

Structural configuration validation requires:

```text
configuration_identity.value() is not empty
```

No other content policy is introduced in Phase 2B-1A.

In particular, the deterministic core does not:

- normalize the string;
- trim whitespace;
- change case;
- hash it;
- assign it;
- derive it from configuration contents;
- interpret embedded naming conventions;
- impose an arbitrary maximum length.

The value is opaque to monitor semantics and is preserved verbatim for
evidence.

Adapters that later serialize configuration identity are responsible for
encoding it faithfully in their chosen external representation.

## 8.4 Allocation consequence

`ConfigurationIdentity` is intentionally variable-size and may use dynamic
storage through `std::string`.

That is consistent with the accepted host-core allocation policy.

This single choice does not authorize unnecessary heap-backed abstraction
elsewhere in the deterministic core.

# 9. Cartesian Physical Values

## 9.1 `Position3`

Conceptual public surface:

```cpp
class Position3 final {
 public:
  constexpr Position3(double x_m, double y_m, double z_m) noexcept;

  [[nodiscard]] constexpr double x_m() const noexcept;
  [[nodiscard]] constexpr double y_m() const noexcept;
  [[nodiscard]] constexpr double z_m() const noexcept;

 private:
  double x_m_;
  double y_m_;
  double z_m_;
};
```

Contract:

- synthetic local Cartesian position;
- components are meters;
- binary64 / C++ `double`;
- no implicit geodetic, ECEF, NED, ENU, latitude/longitude, or operational
  coordinate-frame semantics;
- navigation acceptance and configuration validation apply finite-value rules
  as appropriate.

## 9.2 `Velocity3`

Conceptual public surface:

```cpp
class Velocity3 final {
 public:
  constexpr Velocity3(double x_mps, double y_mps, double z_mps) noexcept;

  [[nodiscard]] constexpr double x_mps() const noexcept;
  [[nodiscard]] constexpr double y_mps() const noexcept;
  [[nodiscard]] constexpr double z_mps() const noexcept;

 private:
  double x_mps_;
  double y_mps_;
  double z_mps_;
};
```

Contract:

- synthetic local Cartesian velocity;
- components are meters per second;
- binary64 / C++ `double`;
- distinct type from `Position3`.

## 9.3 Why not scalar strong-unit wrappers

Phase 2B-1A does not introduce `Meters`, `MetersPerSecond`, or generic quantity
templates.

The distinct Cartesian value types plus unit-bearing accessor names already
provide the required domain distinction for this project.

A stronger units library may be reconsidered only if later implementation or
verification evidence demonstrates a concrete defect that the current design
cannot prevent cleanly.

# 11. Navigation Observation

The logical navigation input fact is one value:

```cpp
struct NavigationObservation final {
  NavigationObservationVersion version;
  NavigationSequence sequence;
  ScenarioTime source_time;
  Position3 position;
  Velocity3 velocity;
  NavigationValidity validity;
  NavigationSourceHealth source_health;
};
```

Contract:

- carries all state needed by the initial navigation-acceptance semantics;
- is an input fact, not automatically accepted navigation state;
- has no separate generated observation identifier;
- sequence plus source time supply the existing observation-ordering identity
  information;
- version metadata is preserved but currently non-authoritative;
- the core does not mutate the observation after submission.

Physical finiteness is not guaranteed merely because the value can be
constructed.

Navigation-observation acceptance validates required physical fields according
to existing requirements.

## 11.1 Accepted navigation representation

The authoritative accepted navigation state is conceptually:

```cpp
std::optional<NavigationObservation>
```

owned by the Navigation State Manager.

Phase 2B-1A does not define a second mutable `AcceptedNavigation` structure
that duplicates:

- sequence;
- source time;
- physical state;
- validity;
- health.

Event-local pre-update and post-update snapshots may be immutable values or
views in later interface design, but they shall not become second authoritative
owners.

# 12. Axis-Aligned Synthetic Envelope

Conceptual declaration:

```cpp
struct AxisAlignedEnvelope final {
  Position3 minimum;
  Position3 maximum;
};
```

Using `Position3` for each bound is intentional: the bounds are positions in
the same synthetic Cartesian frame.

Structural validity requires:

```text
isfinite(minimum.x_m)
isfinite(minimum.y_m)
isfinite(minimum.z_m)
isfinite(maximum.x_m)
isfinite(maximum.y_m)
isfinite(maximum.z_m)

minimum.x_m < maximum.x_m
minimum.y_m < maximum.y_m
minimum.z_m < maximum.z_m
```

No general floating-point epsilon is introduced.

Exact represented equality to a valid configured boundary remains `INSIDE`
when envelope classification is later performed.

No arbitrary absolute coordinate magnitude is imposed.

# 13. Monitor Configuration

Conceptual declaration:

```cpp
struct MonitorConfiguration final {
  ConfigurationIdentity identity;
  ScenarioDuration navigation_freshness_limit;
  ScenarioDuration interface_timeout_limit;
  ScenarioDuration persistence_duration;
  ScenarioDuration projection_horizon;
  AxisAlignedEnvelope envelope;
};
```

All fields are required.

There are no threshold defaults.

## 13.1 Structural validity

A configuration is structurally valid only when:

1. `identity.value()` is non-empty;
2. every envelope component is finite;
3. envelope minimum is strictly less than maximum on each axis.

No separate non-negativity check is needed after the four duration fields have
been validly constructed as `ScenarioDuration`, because that domain type cannot
represent a negative value.

Any future parser or adapter that accepts a signed, textual, or otherwise
untyped duration candidate shall reject a negative value before constructing
`ScenarioDuration`. Converting a negative external value into the unsigned
duration domain through wraparound or modulo conversion is prohibited.

Zero remains valid for every configured duration.

## 13.2 No cross-field policy constraints

Validation shall not invent relationships such as:

```text
interface_timeout_limit > navigation_freshness_limit
persistence_duration < navigation_freshness_limit
projection_horizon < interface_timeout_limit
```

No such relationship is currently required.

## 13.3 Immutability

After successful validation and initialized-execution creation, the active
`MonitorConfiguration` is immutable for that execution.

Explicit reset does not create a new configuration value.

Changing configuration requires creation of a new initialized execution.

# 14. Optional-Value Semantics

The initial C++ design shall use `std::optional<T>` for genuine absence.

Examples include:

```cpp
std::optional<ScenarioTime>
std::optional<NavigationObservation>
```

where the containing state owner needs to represent:

- no accepted runtime-event time yet;
- no accepted navigation observation yet;
- no qualifying interface activity time yet.

Phase 2B-1A shall not encode absence through:

- time `-1`;
- sequence zero;
- version zero;
- empty physical vectors;
- NaN;
- infinity;
- magic configuration identity values.

`ConfigurationIdentity` differs from optional state: active configuration
identity is mandatory, so its empty string is invalid rather than an absence
sentinel.

---

# 15. Physical Finiteness

A reusable pure predicate may be provided conceptually as:

```cpp
[[nodiscard]]
bool is_finite(Position3 value) noexcept;

[[nodiscard]]
bool is_finite(Velocity3 value) noexcept;
```

These predicates contain no monitor policy.

They merely determine whether all components of the supplied physical value are
finite.

Where finiteness affects:

- navigation acceptance;
- configuration validation;
- projection result validity;

the owning semantic path decides the consequence.

---

# 16. Projection-Duration Conversion

Projection is the only current path that converts modeled duration into
floating-point physical time.

Conceptually:

```cpp
[[nodiscard]]
double seconds(ScenarioDuration duration) noexcept;
```

with:

```cpp
static_cast<double>(duration.nanoseconds()) / 1'000'000'000.0
```

The cast and floating-point denominator are explicit so this conversion cannot
silently become integer division.

Contract:

- every `std::uint64_t` nanosecond duration converts to a finite `double`;
- conversion may round because not every integer above the binary64 exact
  integer range is representable exactly;
- that rounding affects projection arithmetic only;
- no modeled-time ordering, freshness, timeout, or persistence boundary uses
  floating-point seconds;
- unit conversion occurs in one clearly defined domain/projection path.

Phase 2B-1A does not claim nanosecond physical accuracy.

---

# 17. Projection Result Representability Boundary

Finite navigation position, finite velocity, and finite converted duration do
not guarantee that:

```text
position + velocity * dt_seconds
```

remains finite in binary64.

The later projection function shall therefore check the computed `Position3`
for finiteness before envelope classification.

If any projected component is non-finite:

- projected envelope status is `NOT_EVALUATED`;
- reason `PROJECTED_POSITION_NONFINITE` applies;
- no projected `INSIDE` or `OUTSIDE` result is produced;
- current-state persistence is unaffected by the failed projection;
- no simulated action is created from the failed projection.

Phase 2B-1A does not solve this by:

- clamping;
- saturating;
- reinterpreting infinity as `OUTSIDE`;
- imposing arbitrary coordinate/velocity/horizon maxima.

# 18. Equality and Comparison Policy

## 18.1 Integral strong values

For:

- `ScenarioTime`;
- `ScenarioDuration`;
- `NavigationSequence`;
- `RuntimeEventReference`;
- `NavigationObservationVersion`;

equality compares the wrapped integral value exactly.

Ordering is defined only where the domain semantics require it.

In particular:

- `ScenarioTime` is ordered;
- `ScenarioDuration` is ordered;
- `NavigationSequence` supports numeric ordering under the initial
  no-rollover policy;
- `RuntimeEventReference` has equality identity semantics but its numeric order
  has no monitor authority;
- `NavigationObservationVersion` numeric ordering has no current behavioral
  authority.

## 18.2 Configuration identity

`ConfigurationIdentity` equality is exact byte-for-byte equality of the stored
`std::string` value.

The deterministic core does not apply:

- case folding;
- whitespace trimming;
- Unicode normalization;
- locale-sensitive comparison.

String ordering has no current monitor authority and is not required as a
domain operation.

## 18.3 Floating-point physical values

The initial domain types do not define approximate equality.

Envelope semantics operate on represented values directly.

Tests that require exact boundary equality shall use deliberately chosen
binary64 values suitable for that purpose.

# 19. Construction Versus Semantic Validation

Not every semantically invalid input must be impossible to represent, but every
public domain value shall still require intentional construction.

Phase 2B-1A separates:

- **construction discipline**, which prevents implicit/default substitution of
  required values;
- **representation validity**, which the chosen storage domain itself can
  guarantee;
- **semantic validity**, which belongs to the relevant validation path.

Examples:

`ScenarioDuration` guarantees non-negativity by representation.

`ConfigurationIdentity` uses an owned string representation; an explicitly
constructed empty identity is representable so complete monitor-configuration
validation can reject it.

`Position3` and `Velocity3` may intentionally contain NaN or infinity before
the relevant semantic validation path rejects those values.

`AxisAlignedEnvelope` may be intentionally constructed before its finite
component and min/max relationships are validated; the configuration validator
owns that structural validation.

Requiring intentional construction is therefore not the same as forcing all
semantic validation into constructors. Constructors establish ownership and
domain separation; explicit validators retain the existing monitor-policy
responsibilities.

---

# 20. Allocation and Ownership Consequences

Most Phase 2B-1A values are fixed-size and trivially ownership-clear.

The exception is:

```text
ConfigurationIdentity -> std::string
```

which owns variable-size storage intentionally.

The initial host-based deterministic core has no baselined heap prohibition,
hard real-time allocation bound, custom allocator requirement, or embedded
memory budget.

Therefore this design does not introduce:

- fixed-capacity string libraries;
- memory pools;
- arenas;
- custom allocators;
- reference-counted polymorphic domain objects.

If a later target introduces a bounded-memory requirement, configuration
identity representation may be revisited through a reviewed interface change.

# 22. Prohibited Accidental Semantics

The concrete type design shall not introduce any of the following:

1. implicit host-clock reads;
2. implicit conversion between absolute time and duration;
3. signed-overflow-dependent time subtraction;
4. sequence rollover behavior;
5. a generated execution identity;
6. a generated configuration identity;
7. a separate generated navigation-observation ID;
8. schema-version rejection policy;
9. hidden threshold defaults;
10. arbitrary configuration maxima;
11. generic floating-point epsilon behavior;
12. projected infinity interpreted as valid envelope evidence;
13. configuration hashing as identity;
14. sentinel values for optional state;
15. a generic monitor operating-state machine;
16. operational aerospace coordinate frames, thresholds, or procedures.

# 24. Critical Review Questions

Before this document is accepted, review shall answer all of the following.

## 24.1 Is configuration identity overdesigned?

If `ConfigurationIdentity` requires hashing, UUID machinery, canonical
serialization, or a fixed capacity without a requirement, the design is too
complex.

## 24.2 Is configuration identity under-owned?

If the initialized execution merely stores a `std::string_view` into caller
memory, ownership and replay stability are weaker than required.

## 24.3 Can strong domain values appear through accidental defaults or implicit conversion?

If a required time, duration, sequence, event reference, schema version,
configuration identity, physical vector, observation, envelope, or monitor
configuration can silently appear through a default or implicit conversion,
the construction surface is weaker than intended.

## 24.4 Can time subtraction invoke signed overflow?

If yes, the arithmetic design is incorrect.

## 24.5 Can a duration become negative?

If yes, the chosen representation is inconsistent with all currently defined
duration semantics.

## 24.6 Can raw integers be accidentally interchanged across time, sequence,
reference, and version domains?

If public interfaces accept those concepts as untyped raw integers, the strong
type design has failed.

## 24.7 Has a generic units or vector framework appeared without need?

If yes, remove it unless a concrete defect requires it.

## 24.8 Has finite-input validation been confused with finite-output projection?

If the design assumes finite projection inputs guarantee a finite projected
position, it violates the Phase 2B-0A correction.

## 24.9 Has schema version gained behavior?

If the numeric version changes navigation acceptance without a requirement,
the design is incorrect.

## 24.10 Has sequence rollover been introduced implicitly?

If maximum sequence followed by zero is accepted as forward progress, the
design violates the current baseline.

## 24.11 Has reset been allowed to replace configuration?

Explicit reset is an in-execution latch-control operation. It shall not become
an implicit configuration-change mechanism.

# 25. Phase 2B-1A Acceptance Criteria

Phase 2B-1A is acceptable when engineering review agrees that:

- every integral domain with materially different semantics has a distinct
  strong type;
- strong wrappers require explicit construction and do not rely on magic
  default values or implicit raw-type conversion;
- required-field composite values do not silently manufacture all-zero or
  omitted-field defaults;
- modeled absolute time remains signed 64-bit nanoseconds;
- modeled duration is unsigned 64-bit nanoseconds;
- every ordered pair of representable scenario times has an exactly
  representable elapsed duration;
- `checked_elapsed_between` returns a result for every ordered time pair and
  `std::nullopt` only for a regressive argument relation;
- checked elapsed-time arithmetic cannot rely on signed overflow;
- no custom error hierarchy is introduced for the single no-result arithmetic
  condition;
- no unchecked time-plus-duration API is required by the current design;
- navigation sequence remains uint64 with no rollover semantics;
- runtime-event reference remains caller-supplied evidence identity only;
- navigation schema version remains metadata only;
- configuration identity is caller-supplied, owned, non-empty, opaque, and
  preserved verbatim;
- no arbitrary configuration-identity length bound is invented;
- position and velocity remain distinct simple Cartesian values;
- no unnecessary units/vector framework is introduced;
- navigation validity and source health preserve the existing closed domains;
- accepted navigation can remain one optional immutable observation value;
- envelope representation preserves exact-boundary semantics and structural
  min/max validation;
- configuration contains all required threshold fields with no silent defaults;
- configured zero durations remain valid;
- projected non-finite arithmetic remains distinguishable from valid projected
  envelope classification;
- optional absence uses explicit optional semantics rather than sentinels;
- no implementation behavior belonging to Phase 2B-1B is prematurely encoded;
- no operational aerospace thresholds or procedures enter the design.

Only after this review passes should Phase 2B-1B freeze concrete runtime-event,
result, evidence, initialization, reset, and coordinator public interfaces.
